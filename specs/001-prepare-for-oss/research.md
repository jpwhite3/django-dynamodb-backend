# Research: Prepare for Open Source Publishing

## 1. Moto vs. LocalStack

**Decision**: Use **LocalStack** for local development and **moto** for unit/integration tests.

**Rationale**:

*   **LocalStack** provides a more realistic local development environment by running a container that emulates a wide range of AWS services. This is ideal for manual testing and for running the application locally in a way that closely mirrors a production serverless environment. The user explicitly chose LocalStack for this purpose.
*   **Moto** is a library that mocks AWS services in memory. It's lightweight and fast, making it perfect for running automated tests in a CI/CD pipeline where speed is important. It's already integrated into the project's development dependencies.

**Conclusion**: We will use both tools for their respective strengths. LocalStack for the `make local-dev` command, and moto for the `make test` command.

## 2. pip-tools Best Practices

**Decision**: Use a `requirements` directory with `base.in`, `base.txt`, `dev.in`, and `dev.txt`.

**Rationale**:

*   Separating production and development requirements is a standard best practice.
*   Using `.in` files for abstract dependencies and `.txt` files for pinned dependencies (generated by `pip-compile`) ensures deterministic builds.
*   The `requirements` directory keeps the root of the project clean.

**Implementation**:

1.  Create a `requirements` directory.
2.  Create `base.in` with production dependencies (e.g., `django`, `boto3`).
3.  Create `dev.in` with development dependencies (e.g., `pytest`, `black`, `flake8`, `pip-tools`, `moto`, `localstack`).
4.  Generate the `.txt` files using `pip-compile`.

## 3. Makefile Best Practices

**Decision**: Create `make` targets for `local-dev`, `stop`, `test`, `lint`, and `format`.

**Rationale**:

*   The `Makefile` will be the single entry point for all common development tasks.
*   The `local-dev` target will use `docker-compose` to start the LocalStack container and the Django development server.
*   The `stop` target will stop the containers started by `local-dev`.
*   The `test` target will run the `pytest` test suite.
*   The `lint` and `format` targets will run `flake8` and `black`.

## 4. GitHub Actions Best Practices

**Decision**: Create a single GitHub Actions workflow file that runs on every push and pull request.

**Rationale**:

*   A single workflow file is sufficient for this project's needs.
*   The workflow will have jobs for:
    *   Linting (`flake8`)
    *   Formatting (`black --check`)
    *   Testing (`pytest`)
*   The testing job will use `moto` to mock AWS services.
*   The workflow will use a matrix strategy to test against multiple Python and Django versions in the future.
